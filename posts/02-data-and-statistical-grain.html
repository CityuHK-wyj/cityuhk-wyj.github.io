数据层：热库、冷库，以及一行究竟代表什么

首发 2026-09-07 · 更新 2026-09-07 · 数据工程
Markdown 原文完整文本

项目已经积累了两类本地历史数据：讨论中报告 2024–2026 年 Statcast 存入 PostgreSQL，2015–2023 年存为 Parquet。这个分层是当时的数据布局，不能直接推导为任何时刻都完整、最新的覆盖承诺。

记录性质： 历史设计与代码回顾；文中的实现改进为本次整理建议。

为什么同时保留 PostgreSQL 和 Parquet

PostgreSQL 适合承载近期数据、球员字典和频繁查询；Parquet 保留历史明细，DuckDB 提供对这些文件的 SQL 分析入口。它们解决的是不同访问需求，不需要把全部历史数据反复搬进同一个数据库。

跨年度查询需要先检查覆盖范围，再拆分执行与合并。例如 2023–2024 的问题会跨冷、热两层。合并时要统一字段类型和统计口径，避免重复边界数据。平均值不能直接平均：应合并有效值总和与有效样本数后再计算。

建议增加覆盖清单： 为每份数据记录赛季、日期上下界、数据粒度、可用字段、最后更新时间、缺失说明和数据版本。Router 应依据清单选择数据源，不能只依赖提示词里的年份分界。

一颗投球不等于一个打席

历史工具说明明确指出：statcast_pitches 的一行是一颗投球。于是 COUNT(*) 统计的是保留下来的投球记录数，不能直接当作 PA。

原型用比赛 ID 与打席序号组成键来计数不同打席。这个规则很有用，但仍需要一个限定：当输入已筛选为某种球速或区域时，计算出来的是“包含这些投球的不同打席数量”。它并不会自动等于标准官方 PA，更不会代表球员整个赛季的 PA。若包含未完成打席，还需要进一步处理。

同样，统计 events = 'home_run' 的记录数，需要确定数据没有重复入库，并确认事件出现在打席结束记录上的方式。一个字段名不能替代对数据粒度的理解。

原始流水与快照各有角色

项目曾使用打击汇总快照，后来更重视逐球数据与 SQL 聚合，因为任意日期、球数、球速和区域条件都难以由固定快照覆盖。球员字典用于连接可读姓名与稳定 ID。

数据 适合回答 需要注意
逐球明细 特定 count、球种、区域下的表现 投球、打席、击球事件粒度不同
打席事件 PA 结果与基础打击统计 打席完整性、重复记录
赛季快照 已发布高阶指标与赛季榜单 获取时间、指标定义和资格标准
球员字典 ID 与姓名映射 多来源 ID、角色与同名
新闻与合同 阵容、伤病、薪资背景 日期、时效性、原始来源

曾出现快照表缺少查询所用字段、姓名反查结果混入投手等问题。它们说明“脚本预期的 schema”与“真实数据库 schema”必须核对，不能让模型按记忆补字段。

数据空白与历史指标

历史年份可能缺少某些指标或有效测量值。查询时必须区分列不存在、列存在但为 NULL、字段只覆盖部分事件，以及筛选条件导致没有结果。

原型还要求 WAR、wRC+ 等复杂高阶指标优先读取已发布数据，因为当前本地数据缺少必要的完整输入。这个限制属于项目数据条件，并不意味着这些指标在数学上永远不能本地计算。只有在输入、定义和版本都齐全后，才有条件讨论可靠复算。

任何时候都不能把缺失值当作零，也不能把联网失败包装成统计事实。
