先弄清楚是谁、什么指标，再考虑 SQL

首发 2026-09-07 · 更新 2026-09-07 · 语义理解
Markdown 原文完整文本

用户说 Hernández、Will 或 Kyle 时，系统未必知道他指谁。项目还讨论过“交通指挥员”这样的社区绰号：在此前对话中，它被用来指 Gerrit Cole。这个映射有上下文和时效性，不能作为全球唯一且永久有效的名称规则。

记录性质： 讨论结论整理；具体字段结构仍属建议。

姓名用于交流，ID 用于连接

已经形成的原则是：实体解析应保留用户原始表达，找到候选球员，再结合球队、赛季、角色和前文确认身份。如果候选仍有多个，向用户提出简短澄清；不要因为某个名字最知名就默默选定。

统一命名规范有价值，但名字变得整齐并不能消除同名。真正用于数据库查询和跨源连接的应是稳定标识，同时记录它属于哪个来源。不同网站的球员 ID 不能仅凭数字相等就直接相连。

可选的实体输出结构可以包含 raw_mention、entity_type、canonical_name、source_ids 和候选依据。这些字段是本次整理提供的实现方向，并非已经确认的正式 schema。

指标语义层与 Schema RAG 是两件事

“平均击球初速”是语义；某张表的 launch_speed 是物理字段。指标语义层需要解释如何选择事件、忽略哪些缺失值、分母是什么、单位是什么；Schema RAG 需要提供真实可用的表、列、关联关系和计算所需字段。

如果只检索列名，模型可能知道使用哪个字段，却不知道该在哪些事件上聚合。如果只提供指标说明，模型可能理解了概念，却编造数据库不存在的字段。因此两层需要协作。

一个可维护的检索单元可以包含：指标含义、适用年份、粒度、数据源、依赖字段、过滤规则、已验证表达式与限制。项目讨论过使用向量检索，也担心一次注入太多说明分散模型注意力；目前没有证据表明向量库选型已经最终确定。

fields 不应被数据库列名完全绑住

讨论中的关键问题是：任务中的 fields 可以描述语义指标，但数据库字段应当受到真实 schema 约束。新闻和半结构化网页并不遵循数据库命名，如果强行把它们放进同一组物理字段，维护成本会快速上升。

本次整理建议： 任务层表达所需信息，数据源适配层负责将它翻译成具体字段或抓取目标。数据库查询通过 Schema RAG 与验证器约束；Web 输出保留原文证据，由受约束的抽取步骤生成结构化字段，再验证日期、单位和来源。

这保留了 LLM 处理非标准文本的能力，同时使最终结果可以核对。它并不要求为所有自然语言短语手写一张穷尽映射表。

歧义应在成本最高的动作之前解决

“高区快速球”至少需要确定球种集合与区域定义；“近 30 天”需要明确截止日期与时区；“表现最好”需要指定评价指标。对于已有明确会话约束的内容应直接复用；对会改变查询结果的关键歧义应澄清或明确披露假设。

不是每个问题都要启动长问卷。要问的是会导致查询对象、过滤条件或统计口径不同的那一点。
