把聊天变成可更新的项目知识，而不是一份越来越长的摘要

首发 2026-09-07 · 更新 2026-09-07 · 知识维护
Markdown 原文完整文本

聊天保留探索过程，博客帮助读者理解设计，而未来参与开发的 LLM 还需要快速识别当前事实。只把所有消息拼到一篇文章里，很容易让旧方案和新结论拥有同样的权重。

记录性质： 本次博客采用的维护约定，不代表原 Agent 的已有实现。

三种内容分别承担责任

连载文章解释问题如何出现、方案为什么变化；current-state.md 记录当前认知和下一步；decisions.md 保留决策 ID、状态、依据与未决问题。历史文章保留原来的讨论背景，重要变化通过新文章和状态页共同体现。

本次整理使用四类表述：历史代码可见、用户讨论已确认、建议方案、待确认。只有看到当前代码与验证结果，才进一步升级为“当前已实现”。这能减少模型把草案当成接口契约的风险。

给 LLM 的入口

llms.txt 是简明导航，llms-full.txt 是本次构建的聚合文本，knowledge/project-state.json 提供机器可读摘要。它们帮助有能力读取这些 URL 的工具获取上下文；不保证所有 LLM 都会自动访问，也不等同于聊天自动同步。

建议阅读顺序是当前状态、决策记录、来源范围，再按任务查相关文章。仓库还保留 AGENTS.md，提醒后续编辑者区分证据层级并同步维护索引。

每次更新做什么

  1. 提供新讨论摘要或可访问的聊天导出，标注日期与来源。
  2. 识别新增事实、被替代的方案和仍未解决的问题。
  3. 需要解释设计变化时新增文章；小范围事实更新可以修改状态页。
  4. 同步决策记录与机器可读状态。
  5. 构建站点，检查内部链接和公开内容，再提交 GitHub。

文章元数据集中在 content/catalog.json。Markdown 是正文的唯一源文件，构建脚本生成网页、原文副本和 LLM 聚合文本，避免手动维护两份正文。GitHub Pages 配置完成后，推送到 main 可触发构建与部署。

全量聊天仍是待补齐的来源

当前能够访问项目记忆摘要、历史原型脚本及一份已有工作流资料，无法枚举并逐字读取本项目全部会话。因此首版是“可访问资料整理”，不是完整聊天档案。与项目没有明确关系的生活、健康、账户等内容不被编入技术博客。

后续拿到完整导出后，应先对照来源索引补齐缺口，再修改对应文章；不要仅因为某条信息在摘要中没有出现，就认定它从未讨论过。
