# 拆解一个问题：两好球、高区快速球、击球初速与薪资

本篇把贯穿项目的复杂问题写成一条可验收的分析路径。它是一份设计演练，**没有执行最新数据查询，也不提供真实球员排名或薪资结果**。

## 第一步：冻结问题口径

| 用户表达 | 需要明确的条件 |
| --- | --- |
| 2025–2026 | 常规赛或包含季后赛；2026 数据截止日 |
| 两好球之后 | 投球前 strikes = 2，对应 0–2、1–2、2–2 |
| 大于 95 mph | 严格大于，不能改为大于等于 |
| 高区快速球 | 球种集合；九宫格上排还是按打者好球带相对高度 |
| 初速最高 | 平均 EV 还是单次最大 EV |
| 前五名 | 有效击球样本门槛、并列处理、不足五人时如何报告 |
| 薪资与性价比 | 赛季、币种、现金收入或 AAV 等薪资口径 |

原始问题里提到九宫格上边缘，实施时应优先延续这项约束，并核对实际区域编码。不能在生成 SQL 时换成另一种“高区”定义。

## 第二步：分清筛选投球与计算样本

先从逐球数据筛出符合 count、球种、球速和区域条件的投球；再根据 EV 指标定义选择具有有效测量值的击球事件。挥空或界外等事件是否进入样本，需要按已确认的指标口径处理，不能靠 `launch_speed IS NOT NULL` 这一条件替代所有语义判断。

假设用户确认按符合条件击球事件的平均 EV 排名，则对每位球员保留 EV 总和、有效样本数和平均值。资格筛选针对这个条件下的有效样本，而全季 qualified 标准可以作为额外条件，二者不能相互替代。

## 第三步：排名完成后再补身份与薪资

本地结果保留稳定球员 ID、年份、指标值、有效样本数和过滤条件。姓名字典用于展示；薪资网站如果采用另一套 ID，需要显式映射与验证。

历史提示词曾要求使用“当前 2026 年薪资”。对跨年分析而言，这条规则需要改进：查询什么赛季，就明确对应哪个薪资时期；若使用当前合同讨论未来价值，应在报告中单独说明，而不能默默把两年表现除以一年薪资。

## 第四步：防止把一个比值写成综合价值

早期原型已经反对“总 EV / 年薪”“总 wOBA / 年薪”这类机械归一化，但又提出可以用“EV 超过联盟均值的部分”比较年薪。后者也只能描述某种自定义比值，不能自动代表球队价值。

这个问题只覆盖特定对球条件下的击球表现，无法直接代表全部进攻、防守、跑垒、出勤和未来贡献。即使引入 WAR 与薪资，也需要交代时期、指标来源、合同结构和分析目标。

因此，第一版更稳妥的输出是并列展示条件内表现、样本与薪资，再写有限的判断；如需综合性价比排名，应另行确认评价方法。这里对旧提示词的修正属于本次编辑建议。

## 第五步：验收完整链路

这条案例可以逐步扩展：先固定赛季与条件验证本地排名，再接入实体映射和薪资，最后加入缺失处理与反馈循环。每一步都留下结构化产物和来源，以便定位失败。

关键回归情形包括：不足五名合格球员、跨冷/热库年份、同名球员、缺少 EV、薪资无日期、接口报错、0 rows，以及筛选条件在计划修订中被意外改变。完成标准是这些情形能得到准确解释，而不只是正常示例能返回一张表。
