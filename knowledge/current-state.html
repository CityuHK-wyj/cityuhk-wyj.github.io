Baseball Agent 当前状态

更新时间：2026-09-07。此页是后续接手的首要上下文。范围为可访问讨论和资料，非当前仓库审计。

目标

构建可解释、可验证的 MLB 数据分析 Agent：保留用户约束，跨 PostgreSQL、Parquet 与 Web 获取证据，通过程序计算指标，再生成带来源与限制的中文回答。

有证据的实现状态

  • 历史脚本存在四工具注册与多轮调用循环：热库、冷库、联网赛季数据、姓名反查。未在本次执行这些代码。
  • 用户曾报告已存入 2024–2026 Statcast 热数据，2015–2023 Parquet 历史数据，以及部分高阶指标。没有验证当前完整性与截止日。
  • 2026-08 的讨论报告新项目骨架主要是占位符，原脚本尚未迁移。当前进度未知。
  • 博客仓库 CityuHK-wyj/cityuhk-wyj.github.io 已创建并授权。博客仓库与 Agent 实现仓库不同；本次仍未审计 Agent 当前代码。

讨论中明确的方向

保留 raw_query；允许 LLM 生成受验证的 SQL；规范化实体但不依赖姓名唯一性；Schema RAG 约束物理字段；采用带类型的任务与结果；记录依赖和来源；以真实工具反馈更新计划；将 0 rows 与错误区分；证据不足时不能生成确定结论；允许对影响结果的歧义向用户澄清。

不要求手工维护过细的 artifact_id 分类。不要将本博客中的 JSON 示例视为已批准 schema。

尚未定稿

AgentTask / ToolResult 正式字段；任务状态迁移；正在执行任务的参数变更规则；检查点存储与恢复；confidence 的定义与阈值；结束预算和非成功结束状态；向量库选型；语义指标与 Web 字段适配的具体接口。

建议的下一步

先读取真实代码与 schema，确认原型现状；然后确定最小 Task/ToolResult 合约，跑通一个本地球员查询，补上只读执行与错误分类；最后逐步扩展到复杂高区快速球案例。此顺序是本次整理建议。
