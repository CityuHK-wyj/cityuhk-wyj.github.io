# 可靠的 Agent 循环：零行、错误与低置信度

项目偏好的工作顺序逐渐明确：先查询相关数据，让模型审阅实际结果，必要时补查 Web，再根据证据决定能否回答。若问题本身就是合同或实时阵容，则应直接路由到合适的联网来源，而不必机械地先查本地。

**记录性质：** 已讨论原则与本次工程建议；没有声称验证器已实现。

## SQL 能写出来，不等于可以执行

项目不希望完全剥夺模型生成 SQL 的能力，因为固定查询模板难以覆盖复杂投球条件。相应地，SQL 的边界需要由程序执行。

讨论计划使用 sqlglot 做解析与校验。这里要区分语法检查与权限保障：AST 合法不能自动证明访问安全，也不能证明统计正确。只读账号、允许访问的表或路径、超时与结果规模限制，需要由执行层落实。

历史原型中，数据库工具直接执行传入字符串，冷库工具还通过字符串替换纠正文件路径。它们是早期便利实现，不应作为后续安全验证已经完成的证据。复杂表达式、函数能力和外部路径需要独立控制。

## 0 rows 是一个待解释的观察

| 观察 | 可能原因 | 下一步 |
| --- | --- | --- |
| 有效执行但没有匹配记录 | 条件确实无匹配 | 核对覆盖范围后报告空集 |
| 对应赛季未加载 | 数据缺失 | 路由到其他来源或说明不可用 |
| 球员匹配失败 | 实体或跨源 ID 错误 | 回到实体解析 |
| 资格门槛后全被排除 | 样本不足 | 展示门槛与限制，修改条件需确认 |
| 查询报错 | SQL、权限或接口失败 | 保留错误类型，修复或停止 |

尤其不能把 API 异常转成空数组，再告诉用户“没有符合条件的球员”。调用失败、未找到和统计上的零是不同状态。

## confidence 应当依赖证据

讨论希望每轮取数后更新 confidence，达到要求再生成报告。尚未确定的是分数的定义、校准方式和阈值。LLM 自报“我有 95% 把握”并不是已校准的可靠性度量。

本次整理建议先使用可核对的门槛：关键实体是否确认、年份是否完整、口径是否明确、样本是否足够、来源是否有效、必需字段是否齐全。模型可以综合解释这些证据，但不能通过抬高分数掩盖缺失。

## 不足时停止，也不能伪装成成功

用户明确反对 confidence 不足时提前输出确定结论。这条原则需要与有界执行同时成立：网络持续失败时，系统不能无限循环。

建议将结束状态区分为“证据充分的回答”“等待用户澄清”“证据不足的说明”“执行失败”。达到最大步数、时间或成本预算，只能触发后面几种状态，不能把它算作分析成功。这是本次整理提出的实现方案，尚待项目确认。

## Formatter 接收已经验证的分析结果

核心指标由查询或 Feature Engine 计算，形成带口径、样本量、来源和限制的 Analytics JSON。Formatter 负责说明结果与不确定性，不在写作时临时重算另一套排名。

一份可信报告应能回答：数据来自哪里、截至何时、覆盖什么、排除了什么、结论依赖哪些假设。优美排版不能弥补这些信息的缺失。
